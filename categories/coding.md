## 一、Java & Spring 专项规范

| # | 规则 |
|---|---|
| 1 | **分层解耦**：严格执行 Controller → Service → Repository；区分 Entity/DTO/VO，修改字段需要同步检查映射 |
| 2 | **Spring 防御**：写操作必须加 `@Transactional`，避开自调用事务失效场景；优先构造器注入 |
| 3 | **健壮性能**：强制使用 Optional 或工具类防止 NPE；IO 资源使用 try-with-resources；Service 保持线程安全 |

## 二、任务执行自检清单 (Checklist)

- [ ] **逻辑一致性**：是否扫描并处理了公共方法引用点的风险？
- [ ] **模型完整性**：Entity/DTO/VO 字段映射是否同步更新？
- [ ] **Spring 事务**：写操作是否有事务？是否存在失效场景？
- [ ] **异常与边界**：Catch 块是否包含上下文？空集合/空对象是否有防御？
- [ ] **依赖最小化**：是否引入冗余依赖或重复造轮子？
- [ ] **代码整洁**：无模糊 `//TODO`、无调试打印、无无用注释

## 三、接口测试要点

### 请求头格式
```
token: {token}
signature: {signature}
timestamp: {timestamp}
nonce: {nonce}
```
**不需要** `Authorization: Bearer {token}`，token 直接放在 `token` 请求头中。

### 测试流程
1. 测试前先**阅读代码 `WebMvcConfig.java`** 查找是否有跳过签名验证的测试凭证
2. 如果代码中有硬编码的测试凭证，就使用它
3. 如果代码中没有，就**询问用户提供有效的 token、signature、timestamp、nonce**
4. 拿到凭证后按照请求头格式进行接口测试

### 记住规则，不记住固定值
- 不硬编码记住具体的 token/signature 值
- 每次测试前先看代码找测试凭证
- 代码中没有就问用户要
- 拿到后按照格式测试

## 四、接口测试完整标准流程

| # | 步骤 | 操作要点 |
|---|------|----------|
| 1 | **查找全局鉴权配置** | - 查找 `WebMvcConfig`、`HandlerInterceptor` 等拦截器配置<br>- 分析 token 解析位置和认证规则<br>- 确认是否需要签名、时间戳、nonce 等额外参数<br>- 如果有测试环境特殊签名绕过规则，记住测试时直接使用 |
| 2 | **启动项目** | ```bash<br>mvn spring-boot:run -Dspring-boot.run.jvmArguments="-Xmx512m" &<br>```<br>- 后台运行，不阻塞终端<br>- 等待启动完成，通过 `lsof -i` 找到监听端口 |
| 3 | **构造正确的 curl 请求** | ```bash<br>curl -s -X POST \<br>  -H "Content-Type: application/json" \<br>  -H "token: {token}" \<br>  -H "timestamp: $(date +%s)" \<br>  -H "nonce: $(head -c 8 /dev/urandom | xxd -p -c 8)" \<br>  -H "signature: {signature}" \<br>  "http://localhost:{port}/{path}" \<br>  -d '{}'<br>``` |
| 4 | **分析返回结果** | - `code: 200` + `success: true` → 接口正常<br>- 根据 `data` 判断业务逻辑是否正确<br>- 空数据返回空 Map/空列表是正常业务结果 |
| 5 | **记录测试结论** | 确认：项目启动 ✅、接口路由 ✅、鉴权通过 ✅、代码逻辑 ✅、返回结构 ✅ |

## 五、多分支同步差异对比流程

| # | 步骤 | 操作要点 |
|---|------|----------|
| 1 | **明确目标分支特性** | - 先确认当前分支是什么角色（**判断依据见下表**）<br>- 理解两个分支的定位差异 |
| 2 | **查看原分支提交内容** | - `git log sourceBranch --oneline -N` 查看最近N次提交<br>- `git show commitHash` 查看每个提交具体改了什么 |
| 3 | **对比功能差异** | - 原分支新增/修改了什么功能？<br>- 当前分支原有特性是什么？<br>- 哪些功能需要保留当前分支特性？<br>- 哪些功能需要和原分支保持一致？ |
| 4 | **合并原则** | - 接口返回结构、方法签名保持和原分支一致<br>- 数据权限过滤保持当前分支特性<br>- 业务逻辑适配当前分支定位（学校管理员端看全校，教师端只看自己关联班级） |
| 5 | **验证差异** | - 合并后检查：返回结构一致 ✓、权限逻辑正确 ✓、当前分支特性保留 ✓ |

### 分支角色判断原则

**判断顺序（优先级从高到低：**
1. 第一步看 `application.properties` / `bootstrap.yml` 中的 `spring.application.name` → **实际配置优先级最高**
2. 第二步看分支名称 → 辅助确认角色定位
3. 第三步确认数据权限特性 → 选择正确的过滤逻辑

**核心原则：实际配置 > 分支命名约定**，因为配置是运行时真实生效的，命名只是约定。

## 六、设计模式：逐步缩小查询范围

适用于 **"多表关联、条件分散"** 的查询场景优化。

### 设计思路

```
1. 查询主表信息 → 得到初步筛选后的ID列表
2. 根据ID查询关联表 + 在关联表上添加过滤条件 → 进一步筛选
3. 根据过滤后的关联反向过滤主信息 → 得到最终结果列表
4. 从关联提取主键 → IN查询详细信息 → 已经是精确主键查询，不需要其他条件
```

### 核心思想

- **谁有过滤条件谁先过滤**：过滤条件在哪个表，就在哪个表过滤
- **逐步缩小范围**：每一步都过滤掉不符合条件的数据，下一步数据量更少
- **最后精确查询**：到最后一步已经是主键IN查询，效率最高
- **减少数据传输**：每一步过滤，最终查询数据量最小

### 通用性

这个思路**非常通用**，可以推广到所有"多表关联、条件分散"的查询场景：
- 商品搜索：`分类 → 属性关联 → 商品`
- 订单查询：`用户 → 地址 → 订单`
- 权限管理：`角色 → 权限关联 → 菜单`
- 文章搜索：`标签 → 标签关联 → 文章`

### 对比其他方案

| 方案 | 问题 |
|------|------|
| 多表JOIN一次查出 | SQL复杂，优化器可能选错索引，大数据量性能差 |
| 先查全量再内存过滤 | 查出大量不需要数据，占用内存网络 |
| **逐步缩小范围** | 每一步都用索引，数据量逐步减少，最终精确查询，性能最优 |

## 七、演进式开发方法论

### 核心流程

```
发现问题 → 定位问题 → 修复问题 → 验证效果 → （发现新问题循环）
尝试实现基本功能 → 发现问题 → 分析问题根源 → 修复优化 → 再重构简化 → 验证效果
```

### 核心特点

- **问题驱动，逐步迭代**：小步快跑，不一次性改完所有问题，发现一个解决一个
- **细粒度提交**：每个提交只解决一个问题，便于回滚和追踪
- **先可用后优化**：先保证功能可用，再优化代码结构
- **持续重构**：不满足于"能用"，持续优化代码结构
- **用户中心**：根据实际使用反馈调整设计，不固守初始方案
- **预防胜于修复**：添加前置检查，避免已知的数据问题
- **遵循设计原则**：单一职责、消除重复、代码简洁

## 八、批量数据处理优化实践

适用于**批量数据改造、数据清洗、迁移、批量更新**等场景。这些优化实践来自OSS预览图永久化改造项目，具有普遍通用性。

### 常见问题与优化方案

| 序号 | 问题 | 根因 | 解决方案 |
|-----|------|------|---------|
| 1 | 查询了太多无用字段，浪费内存 | `this.page()` 没加 `select`，查询所有字段 | **只select需要的字段**：只查询本次处理需要的字段，不需要的不要查 |
| 2 | 失败记录不方便重跑 | 没有保存失败id列表，日志大了难以查找 | **收集失败ID方便重跑**：增加 `List<Long> failedIds` 收集所有失败id，最后日志输出，方便只重跑失败项 |
| 3 | 生成失败没更新数据库，一直卡在旧链接 | 生成失败走catch，没有更新任何东西 | **失败只记录不更新**：只记录失败id，不修改原有数据，方便后续重跑 |
| 4 | 逐行更新性能差 | 每条update一次，频繁IO | **批量更新代替逐行更新**：收集需要更新的列表，最后 `updateBatchById` 批量更新，减少数据库IO次数 |
| 5 | 分页判断逻辑容易出错 | 写法容易理解错，可能导致死循环 | **双层保险分页判断**：保持 `(空页 + 最后页)` 双层判断，两层保险，不会死循环 |
| 6 | 失败直接抛出，整个批次卡住 | 一个失败导致整个批次中断 | **失败安全回退**：单个记录失败不阻塞，继续处理下一个，最后汇总失败id，提升整体健壮性 |
| 7 | 出问题不好排查 | 关键步骤没有日志，出问题只能猜 | **完整日志覆盖**：每个关键步骤都打日志，方便排查问题 |

### 最佳实践总结

1. **最小数据原则**：只查询处理需要的最小字段集合，不查询无用字段
2. **失败隔离原则**：单个记录失败不影响整个批次，失败记录单独收集方便重跑
3. **批量IO原则**：攒够一批再一次性更新数据库，减少IO次数，提升性能
4. **防御式编程**：每个环节都考虑失败情况，设计回退方案，不锁死
5. **可观测性**：关键步骤打日志，失败信息明确，方便排查

### 分页遍历模板代码

```java
int pageNum = 1;
int pageSize = 100;
while (true) {
    IPage<Entity> page = this.page(new Page<>(pageNum, pageSize), queryWrapper);
    List<Entity> records = page.getRecords();
    if (records == null || records.isEmpty()) {
        break;
    }
    // 处理当前页数据...
    for (Entity record : records) {
        try {
            // 处理单条记录...
        } catch (Exception e) {
            log.error("处理记录失败，id: {}", record.getId(), e);
            failedIds.add(record.getId());
        }
    }
    // 已经是最后一页，退出
    if (records.size() < pageSize) {
        break;
    }
    pageNum++;
}
// 最后输出失败id列表，方便重跑
log.info("批量处理完成，失败记录id列表: {}", failedIds);
```

## 九、MyBatis / SQL 优化实战

### 1. UNION ALL 联合查询：展示字段与排序字段分离

**问题**：UNION ALL 合并多表查询时，某字段混合了两种形态（如 `@张三` 与 `2026-07-10 14:23:11`），`ORDER BY` 按字符串排序导致 `@` 类记录（ASCII 64 > 数字 48-57）在 DESC 下永远置顶，违背"按时间倒序"直觉。

**通用原则**：混合 SQL 输出中，凡是"展示格式"与"排序语义"冲突的字段，必须拆分为两列——`xxx_display` 给前端渲染，`xxx_sort` 给 ORDER BY（真实类型如 datetime/int）。

### 2. `LIKE '%xxx%'` 前后通配的索引分级策略

MySQL B-Tree 索引对前缀 LIKE 有效，对前后通配 LIKE 完全失效。按数据量分级：

| 数据量级 | 方案 |
|---|---|
| < 10 万条/表 | **复合索引**：`(高选择度列, ..., 目标列)` 先缩小候选集再 LIKE 过滤，性能足够 |
| 10 万 ~ 千万 | 全文索引 `FULLTEXT` + `MATCH...AGAINST`（中文需 ngram 分词器） |
| 千万级+ / 高频搜索 | 外部搜索引擎（ES）+ 数据同步 |

**通用原则**：索引不能让 LIKE 走索引，但能缩小 LIKE 的候选集；数据量未突破量级前不做过度设计。

### 3. 函数计算列的存储层规范化（FROM_BASE64 类）

**双重问题**：查询时每行执行 `FROM_BASE64 + CONVERT`——函数计算无法走索引 + 每行 CPU 开销累积；且 Base64 存储违背"存储即可读"原则（DBA 无法直读、无法建索引/ LIKE、应用层每次读都要解码）。

**通用原则**：存储层承担规范化职责，写入时就把编码/解密/规范化做完，读取路径尽量少函数计算。Base64 只用于传输，不用于存储。类似坏味道：数据库存 JSON 字符串每次读都 `JSON_EXTRACT`，应拆为独立列。

### 4. 雪花算法 Long ID 精度丢失

前端 JavaScript Number 范围有限（2^53），雪花算法生成的 Long ID 传给前端会丢失精度。**解决**：前后端交互统一使用 String 传输 ID。

### 5. 自定义 XML batchInsert 不触发 MyBatis-Plus ASSIGN_ID

MyBatis-Plus 的 `@TableId(type = IdType.ASSIGN_ID)` 雪花 ID 拦截器只在**内置方法**（`insert`/`saveBatch` 等）时生效；自定义 XML SQL 走原生流程，实体 id 为 null 直接进 SQL 触发非空约束错误。

**解决**：批量场景在 Java 侧手动 `IdWorker.getId()` 分配 ID。**衍生教训**：外键依赖主表 ID 时，ID 必须在批量插入前于 Java 侧确定，不能依赖 DB 回填（自定义 XML 也不会像 `useGeneratedKeys` 那样回写实体）。

### 附：优先级评估口诀（集中兵力）

1. **主要矛盾**：正在造成业务错误吗？→ 立即处理
2. **次要矛盾**：会随数据量增长变严重吗？→ 本迭代处理
3. **潜在矛盾**：需要跨模块/新写入侧改造？→ 独立立项，不与本次任务混批

## 十一、类形态设计三问

评估一个类/一组方法该以什么形态存在时，依次回答三个问题：

1. **纯函数吗？**（无状态、无依赖、无 IO）→ util 静态工具类
2. **有 IO 或运行时状态吗？**（读库、落库、进度跟踪、计数器）→ Spring Bean
3. **只有一个调用类且无上下游循环依赖吗？** → 直接内联为调用类的私有方法/嵌套 record

**权重教训**：调用方分布与复用前景的权重**高于**方法本身的薄厚——首次评估只看"方法薄厚"推荐保持独立 Service 被用户以"单一调用方、无复用前景"正确反驳后收回。
**反向案例**：有 2 个互为上下游的调用方时，内联会产生循环依赖/接口污染——先核实调用链再下结论。
